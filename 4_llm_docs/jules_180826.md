# Grasshopper ScriptEditor Bridge Scripts & Code Standardization

**Date**: 18-08-2026

## Objective
Standardize the codebase to properly manage Grasshopper scripts externally via IDEs by abstracting the Grasshopper component files to mere "shells".

## Actions Taken
1. **Standardized Existing Scripts**:
   - Iterated over all Python scripts in `2_grasshopper_scripts/0_scripts`.
   - Updated the `try...except NameError: pass` `ghenv.Component` metadata block to include standard configuration.
   - Enforced `Category` as `"CustomLib"` and `SubCategory` derived from the parent directory structure of each script (e.g. `grid` -> `Grid`).
2. **Generated ScriptEditor Shells**:
   - Created a new parallel directory structure in `2_grasshopper_scripts/ScriptEditor`.
   - For every script found in `0_scripts`, a corresponding shell script was created in `ScriptEditor`.
   - The shell scripts preserve the standardized docstrings and `ghenv.Component` definitions for UI generation.
   - Incorporated dynamic bridge code logic to load and `exec()` the underlying script in `0_scripts` relative to the component's filepath. This legacy execution context securely supports dynamic/optional global input checks from the old scripts without requiring breaking code refactors.
   - **Crucial Update**: Added native Rhino 8 ScriptEditor pragmas (`#! python 3`, `# category: ...`, `# subcategory: ...`) to the absolute top of the shell scripts. This guarantees that when compiling the `.gha`, Rhino 8 correctly categorizes the components in the Ribbon (overriding the default behavior where it ignores `ghenv.Component.Category`).
3. **Web Documentation Updates**:
   - Built the web docs using `python3 build.py`.

## Outcomes
The codebase supports a clean external IDE development flow. Component shells compile flawlessly in Rhino 8 with correct UI layout and Category/Subcategory assignments, bridging seamlessly to procedural python scripts located externally.
